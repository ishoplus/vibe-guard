# 需求访谈：把想法问成一页 SPEC

新手说「做个记账 app」时，里面藏着二十个没人做过的决定。AI 如果默默替用户决定，等发现不对时已经很难改。这个技能的产出是一份用户**读得懂、能拍板**的 SPEC.md。

## 何时不使用
- 需求已经很具体（「把按钮改成蓝色」「加一个导出 CSV」）→ 直接 small-steps
- 项目已有 SPEC.md 且这次只是加功能 → 读现有 SPEC，只针对新功能问 1–3 个问题

## 执行流程

1. **复述**：用一句话复述你理解的想法，确认方向没跑偏。
2. **分轮提问**：从 `references/question-bank.md` 挑问题。规则：
   - 每轮最多 3 个问题，用纯文字条列，每个问题附**选项 + 你的建议 + 为什么 + 选错了会怎样**，让用户可以只回「照你建议」
   - 「选错了会怎样」要具体，并说明以后改起来难不难（例：「选了只存在这台电脑，以后要换成多设备同步，需要把数据搬家」）
   - 先问「会改变整体架构」的（谁用、数据存哪、要不要登录、多设备），细节放后面
   - 用户答「不知道」时，替用户选最简单、最容易以后改的方案，并标注「以后可以改」
   - 总共不超过 3 轮。问不完的写进 SPEC 的「待定」
3. **砍范围**：主动提出「第一版只做这些」，把其余放进「以后再说」。新手的第一版越小越容易成功。
4. **写 SPEC.md**：照 `templates/SPEC.md` 的结构写到项目根目录。全文白话，不出现框架名以外的术语；用到的术语当场解释。
5. **定技术方案**：在 SPEC 的「怎么做」一节，用白话写出选型和理由（例：「用 Supabase 存数据 —— 一个现成的在线数据库，免费额度够用，不用自己管服务器」）。优先选**新手能自己部署、出错有人问得到**的主流方案。
6. **请用户确认**：让用户读一遍，确认后才开始写代码。项目还不是 git 项目时，下一步接 safe-start。

## 资深模式
session 显示「资深模式」时：校验、检查、确认步骤一律照做，只省略教学性说明（白话类比、四段说明、术语解释）。本技能具体差异：
- 只问从代码和描述里推不出来、又会影响架构的决定（数据归属、多用户、鉴权、预算），一轮问完；选项不附教学说明
- SPEC.md 可以写成要点清单，技术方案直接写选型，不写「为什么选它」的白话解释
- 风险一节照写（钱、个人数据、鉴权、对外开放）—— 这是校验，不是教学

## 深度参考

| 文件 | 何时去读 |
|---|---|
| `references/question-bank.md` | 第 2 步挑问题时 |
| `templates/SPEC.md` | 第 4 步写文档时 |

## 硬性纪律
- 不许一次丢超过 3 个问题 —— 新手会被吓跑，或者乱答
- 不许在用户确认 SPEC 前写业务代码
- 涉及**钱、个人隐私数据、账号登录、给别人用**任一项，必须在 SPEC 的「风险」一节写明，并提醒上线前要跑 ship-check
