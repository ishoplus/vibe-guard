# 出事急救

出事时新手最常犯的两个错：慌着修代码而不先止血；为了「看起来没事」删掉证据或瞒着用户。
这个流程的顺序是固定的：**止血 → 评估 → 修复 → 复盘**。止血优先于找原因。

## 执行流程

### 0. 稳住，定位是哪一种
先用一两句话安抚用户，然后问清楚（能自己查的就自己查，不要一次丢一堆问题）：
- 发生了什么现象？从什么时候开始？
- 最近做过什么：上线了新版本？改了设置？改了数据库？
然后归到下面一类，读 `references/playbooks.md` 对应段落：

| 类型 | 典型说法 |
|---|---|
| A. 网站打不开 / 大面积报错 | 「挂了」「白屏」「全是 500」 |
| B. 账单暴涨 / 被盗刷 | 「扣了好多钱」「额度用光了」 |
| C. 密钥外泄 | 「密钥推到 GitHub 了」「收到泄露警告邮件」 |
| D. 数据被看光 / 被改 / 被删 | 「别人看到我的数据」「数据不见了」 |
| E. 被攻击 / 刷量 / 垃圾注册 | 「一堆假账号」「流量暴增」 |

几类同时发生时（例如密钥外泄导致被盗刷），按 C → B → 其他的顺序处理。

### 1. 止血（最优先，几分钟内完成）
照 playbook 的「止血」一节做。原则：
- **可逆的止血动作可以先做**：回滚到上一版、暂停服务、临时关闭注册、调低额度
- **不可逆的动作先问用户**：删除数据、删除账号、重置数据库
- 需要用户在服务后台操作的，给出一步一步的指引；看不到后台就请用户截图
- 每个止血动作都用一句话讲清楚「为什么现在要做这个、做了会有什么副作用」（例：「先把网站退回上一版 —— 这样用户马上能正常使用，代价是刚上线的新功能暂时消失」）。出事时用户很慌，要短，但不能省略副作用

### 2. 记录
在项目根目录建 / 追加 `INCIDENTS.md`，边做边记时间线（几点发现、做了什么、结果如何）。**不要删除日志、不要改动出事现场的数据**，查原因要用。

### 3. 评估影响
- 影响了哪些用户、哪些数据、多长时间、花了多少钱
- 涉及用户个人信息外泄时，读 playbook D 的「要不要通知」一节，**如实**告诉用户（项目主人）法律上可能的义务，由用户决定，不要建议隐瞒

### 4. 修复根本原因
止血之后才开始修。修复按 debug-rescue 的方式找证据、不猜；修好的代码走 ship-check 再上线（部署闸门会检查）。

### 5. 复盘（固定格式，写进 INCIDENTS.md）

```
## {日期} {一句话标题}
- 发生了什么（用户视角）：
- 时间线：
- 根本原因：
- 影响：{多少用户 / 什么数据 / 多少钱 / 多久}
- 怎么止血的：
- 怎么修的：
- 以后怎么防：{具体到「加了什么检查 / 设了什么上限」}
```

「以后怎么防」里的每一条，都要落实成一个具体改动或设置，并把重要的一条写进 AGENTS.md 的「已知问题 / 待办」或规则里。

## 资深模式
session 显示「资深模式」时：校验、检查、确认步骤一律照做，只省略教学性说明（白话类比、四段说明、术语解释）。本技能具体差异：
- 流程不变：止血 → 记录 → 评估 → 修复 → 复盘；止血动作仍要标出副作用，但一行即可
- 不解释事故类型的背景知识，直接给操作步骤
- 个人信息外泄的通知义务照样提出 —— 这是合规判断，不是教学

## 硬性纪律
- 止血之前不修代码
- 不删日志、不删证据、不建议对受影响的人隐瞒
- 不可逆的操作一律先问用户
- 密钥外泄时，「从代码和 git 历史里删掉」**不算**处理完成 —— 必须作废重发
