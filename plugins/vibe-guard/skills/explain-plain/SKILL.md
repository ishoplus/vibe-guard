# 白话解释

目标不只是让用户「这次听懂」，而是让对方**下次能自己判断一部分**。每次解释都是一次小教学。

## 执行流程

先判断用户要解释的是哪一类，然后照对应格式回答。

### A. 报错
```
📍 哪里出错：{用户能对应得上的位置，例：「点保存按钮时，存数据那一步」}
🗣 白话意思：{一句话，例：「程序想去读一个叫 user 的东西，但它是空的」}
🤔 常见原因：{1–3 个，最可能的放前面}
👉 接下来：{你要做什么，或需要用户提供什么}
```
先查 `references/common-errors.md` 有没有对应条目。

### E. 一个建议或步骤（「为什么要这样做」「不做会怎样」「一定要吗」）
先查 `references/why-library.md` 有没有现成的说明，有就照着讲（换成项目里的具体内容）。没有就按同样的四段自己写：
```
📌 要做什么：{用户视角的一个动作}
❓ 为什么：{背后的原因，能用类比就用类比}
✅ 做了之后：{用户能看到或得到什么}
⚠️ 不做的话：{具体后果} —— {很常见 / 偶尔 / 少见但严重}
```
用户问「一定要吗」时，**如实回答**：风险小的就说「可以先跳过，以后再补」，并说清楚什么情况下必须补。不要为了让用户照做而夸大风险。

### B. 概念
用**生活类比 + 在这个项目里的具体位置**解释，控制在 5 句以内。
例：「数据库就像一个共享的 Excel 表 —— 在你的项目里，每一笔记账就是 records 表里的一行。」
术语对照查 `references/glossary.md`。

### C. 刚才的改动
不要贴 diff。用「之前 → 现在 → 为什么」三段说：
- 之前：程序是怎么做的（用户视角）
- 现在：改成怎么做
- 为什么：解决了什么、有什么代价

有风险或取舍的，单独标出来。

### D. 一段代码 / 一个文件
说清楚：它**负责什么**、**谁会用到它**、**改它会影响哪里**。不逐行讲。

## 收尾
每次解释后，附一句「💡 记住这个」—— 一个用户下次遇到类似情况能自己用上的判断方法。
例：「💡 报错里有 `undefined`，通常意思是『东西还没拿到就先用了』。」

## 资深模式
session 显示「资深模式」时：校验、检查、确认步骤一律照做，只省略教学性说明（白话类比、四段说明、术语解释）。本技能具体差异：
- 用户明确问了才解释；直接给技术答案，不用生活类比、不加「💡 记住这个」
- 报错：给根因、证据位置、修法；概念：给准确定义和在本项目中的位置
- 用户问「为什么要做 X」时，一两句讲清收益和不做的风险即可，不必套四段格式

## 深度参考

| 文件 | 何时去读 |
|---|---|
| `references/common-errors.md` | 解释报错时 |
| `references/glossary.md` | 解释概念、需要统一用词时 |
| `references/why-library.md` | 解释一个建议或步骤（E 类）；其他技能要讲「为什么要做」时也来这里查 |

## 硬性纪律
- 不确定报错原因时，说「最可能是…，需要验证」，不要把猜测讲成事实
- 不用术语解释术语；实在要用，那个术语也要当场解释
