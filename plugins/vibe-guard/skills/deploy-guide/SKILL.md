# 第一次部署

新手部署最常见的三个坑：本地能跑、线上坏掉（环境变量没设）；测试时把正式数据弄乱（环境没分开）；出事了不知道怎么退（没找过回滚按钮）。这个流程把三件事都在第一次部署时做掉。

## 执行流程

这个流程里很多步骤，新手第一反应会是「有必要吗？」（分环境、回滚演练、监控、CI）。每一步开始前，先用四段说明讲清楚要做什么、为什么、做了之后的效果、不做的风险；标准讲法见 `../explain-plain/references/why-library.md`。用户决定跳过某一步时，记进 AGENTS.md「已知问题 / 待办」，写明跳过的风险。

### 1. 前置：先过上线前检查
没做过 ship-check，或做完之后又改过代码，先跑 ship-check。vibe-guard 的部署闸门会在部署命令时检查这一点，但最好在开始前就处理掉。

### 2. 选平台
读 `references/platform-picker.md`，按「项目是什么 + 用户在哪里」推荐**一个**平台，用白话说明为什么选它、免费额度多少、超出后会怎样。
- 用户主要在中国大陆：一定要讲清楚「境外平台在大陆访问可能慢或不稳定」和「国内云服务需要 ICP 备案」这个取舍，让用户拍板
- 不推荐新手自己租服务器（VPS），原因见 platform-picker

### 3. 分开测试与正式环境
读 `references/environments.md`。至少做到：
- 正式环境用**独立的数据库**（Supabase / Neon 等开一个单独的 project），测试时不会碰到真实用户数据
- 平台的预览部署（Preview）接测试数据库，正式部署（Production）接正式数据库

### 4. 连接部署方式
优先用「连 GitHub、推送就自动部署」—— 最不容易出错，也天然有每个版本的记录可以回滚。
连好之后，**必须**记录部署方式（这让 vibe-guard 把 `git push` 到正式分支当成「上线」来把关）：

```bash
python3 scripts/record_deploy.py <项目根目录> --platform <平台> --url <正式网址> --auto-deploy-branch main
```

同时告诉用户一句话：「从现在起，推到 main 分支就等于上线。」

### 5. 环境变量
读 `.env.example` 列出所有变量名，带用户逐个在平台的环境变量设置里填上（Production 填正式值，Preview 填测试值）。
- 带公开前缀（`NEXT_PUBLIC_`、`VITE_` 等）的变量会进浏览器，只能放可以公开的值
- **不要让用户把密钥贴进对话里**，让用户直接在平台后台填

### 6. 数据库表结构变更
项目有数据库、这次部署要改表结构时，读 `references/environments.md` 的「改数据库表结构」一节，照「先测试库、先备份、只加不删」的顺序做。

### 7. 部署 + 冒烟测试
部署完成后：
```bash
python3 scripts/smoke_test.py <正式网址> <关键页面路径...>
```
有 🔴 就先处理（或直接回滚）。然后**亲手**走一遍核心流程（注册、下单、存一笔数据），并请用户在手机上也打开一次。

### 8. 找到回滚按钮并演练
带用户在平台后台找到「回到上一个版本」的操作，**实际演练一次**（回滚到上一版，确认网站正常，再切回来）。然后记录下来：
```bash
python3 scripts/record_deploy.py <项目根目录> --platform <平台> --url <正式网址> --auto-deploy-branch main --rollback "<白话步骤>"
```
第一次部署没有「上一个版本」可退时，下次部署后再补演练。

### 9. 监控
读 `references/monitoring.md`，至少设好：错误通知（Sentry 或平台自带的）、网站存活监控（挂了会发通知）、费用告警（ship-check 时应已设好，这里再确认一次）。

### 10. 自动测试（可选，项目有测试时建议做）
项目有测试的话，读 `references/ci.md`，加一个「推送时自动跑测试」的设置，测试不过就不部署。

### 11. 写进项目说明书
在 AGENTS.md 加一节「上线与回滚」：平台、正式网址、哪个分支会自动上线、环境变量**名称**清单（不写值）、回滚步骤、监控在哪里看。

## 资深模式
session 显示「资深模式」时：校验、检查、确认步骤一律照做，只省略教学性说明（白话类比、四段说明、术语解释）。本技能具体差异：
- 步骤清单照走，但只说明结论和需要用户操作的地方，不解释为什么要分环境、为什么要演练回滚
- 用户跳过某一步时，照样记进 AGENTS.md 并写一行风险
- 冒烟测试、`record_deploy.py`（部署闸门依赖它）、回滚记录照做

## 硬性纪律
- 冒烟测试有 🔴、或核心流程亲手走不通，不算部署完成
- 没找到回滚方法，不算部署完成（第一次部署可以标注「下次补演练」）
- 不在正式数据库上手动改表结构；改之前必须有能恢复的备份
- 不让用户把密钥贴进对话
