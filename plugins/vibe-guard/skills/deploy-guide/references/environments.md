# 环境与数据库变更

## 三个环境

| 环境 | 在哪里 | 接哪个数据库 | 谁在用 |
|---|---|---|---|
| 本机开发 | 自己电脑 `localhost` | 测试数据库 | 只有自己 |
| 预览（Preview） | 平台为每个分支 / PR 生成的临时网址 | 测试数据库 | 自己和帮忙测试的人 |
| 正式（Production） | 正式网址 | **正式数据库** | 真实用户 |

**要点**
- 正式数据库只接正式环境。本机和预览都不能连正式数据库 —— 否则测试时的误操作会直接改到真实用户的数据
- 预览网址也是公开的，别在预览环境放真实用户数据
- 环境变量在平台上按环境分别设置（大多数平台可以对 Production / Preview 填不同的值）

## 改数据库表结构（migration）

「表结构」就是数据库里有哪些表、每张表有哪些栏位。改它是上线后最容易丢数据的操作。

### 做法
1. **用 migration 文件，不要手动改**：每次改动写成一个文件（Supabase 的 `supabase/migrations/`、Prisma 的 `prisma/migrations/` 等），跟着代码一起进 git。不在正式数据库的后台界面里手动加减栏位
2. **先在测试数据库跑一遍**，确认网站正常
3. **正式数据库先备份**，并确认知道怎么恢复
4. **只加不删**：
   - 加新栏位、新表 → 安全
   - 改栏位名称 → 拆成「加新栏位 → 代码改用新栏位 → 上线稳定后再删旧栏位」三次做
   - 删栏位、删表 → 先确认代码已经完全不用它、上线稳定一段时间后再删
5. **新栏位给默认值或允许为空**，否则已有的数据会让变更失败
6. 跑完后按冒烟测试和核心流程验证一次

### vibe-guard 会拦的命令
`prisma migrate reset`、`supabase db reset`、`DROP TABLE`、不带条件的 `DELETE FROM` 等都会先要求确认。如果确认框里的命令是对着**正式数据库**，一律先停下来备份。
