# 上线前检查

上线之前的问题，大多只是「不好用」；上线之后遇到的是安全问题：数据被人看光、密钥被盗刷、账单爆炸。这些问题**平时完全看不出来**，所以必须在上线前主动查一次。

## 执行流程

1. **自动检查**：`python3 scripts/precheck.py <项目根目录> --online`。有 🔴 时脚本退出码为 1。
   - `--online` 会联网检查依赖：跑 npm audit / pip-audit，并逐个确认依赖包在 npm / PyPI 上真实存在、不是刚冒出来的冷门包（AI 可能编出不存在的包名，攻击者会抢注这些名字放恶意代码）。连不上网时去掉 `--online`，并告诉用户依赖没查
   - 结果会写进 `.vibe-guard/ship-check.json`。之后执行部署命令时，vibe-guard 会检查：有没有做过检查、还有没有 🔴、检查之后代码有没有再改过 —— 不满足就在确认时明确警告
2. **逐条处理 🔴**：每条先用四段说明告诉用户 —— 要修什么、为什么（谁可能利用它、怎么利用）、修好之后的效果、不修的后果（多常见、多严重）；标准讲法见 `../explain-plain/references/why-library.md`。然后按 small-steps 修。
   - 密钥已泄露（在 git 历史里 / 已推到 GitHub）→ **第一优先是作废重发密钥**，清理历史是次要的
   - 修完重跑脚本，直到没有 🔴
3. **代码审查（按平台调用内置工具）**：precheck 查的是配置和密钥，代码本身的漏洞（注入、越权、XSS 等）交给平台的审查工具：
   - **Claude Code**：调用 `security-review` 技能。它审查当前分支上还没合并的改动；如果项目一直直接在 main 上开发，先向用户说明审查范围，必要时改成逐个审查核心文件（登录、付款、存数据）
   - **Codex**：调用内置的 `review-agent` 技能审查改动；或请用户输入 `/review`（斜杠命令只能由用户输入）
   - 审查发现的问题，按风险用白话转述给用户，和 🔴 一样修完再往下走
4. **人工清单**：读 `references/manual-checklist.md`，按项目实际用到的东西挑出适用项，逐条带用户确认。需要用户花时间去做的项目（设预算、开备份、演练恢复等），先用四段说明讲清楚值不值得做。需要用户去服务后台操作的，给出具体步骤；看不到后台就请用户截图。
5. **平台专项**：用到 Supabase / Firebase / Vercel / Netlify / Stripe / AI API 的，读 `references/platform-notes.md` 对应段落。
   已经有预览网址（或正式网址）时，再跑一次线上检查：`python3 ../deploy-guide/scripts/smoke_test.py <网址>`，它会查 HTTPS、安全响应头、.env / .git 有没有被公开
6. **给结论**（固定格式）：

```
🚦 结论：可以上线 / 修完 N 项后可以上线 / 不建议上线
🔴 已修好：...
🟡 用户已知情并接受的风险：{每条写清楚「不做的话会怎样」，让用户知道自己接受的是什么}
📋 上线后第一周要做：{例：每天看一次费用和错误监控}
```

7. **上线操作本身**：第一次上线，或要改部署方式时，接着走 deploy-guide。发布命令（包括推到会自动上线的分支）会被 vibe-guard 的 hook 拦下来要求确认（Claude Code 弹出确认框；Codex 要你在对话里问用户，用户同意后才能加 `VIBE_GUARD_CONFIRMED=1` 重跑）。

## 资深模式
session 显示「资深模式」时：校验、检查、确认步骤一律照做，只省略教学性说明（白话类比、四段说明、术语解释）。本技能具体差异：
- 所有自动检查、代码审查、人工清单照做，结论格式照写 —— 校验不因模式而减少
- 🔴 逐条列出：问题、影响、修法，各一行；不用四段说明
- 人工清单直接给勾选表，由用户自行确认，只对不确定的项目追问

## 硬性纪律
- 有 🔴 未修，不给「可以上线」的结论。用户坚持要上线时，把风险用白话讲清楚，由用户自己决定并记录进结论的 🟡
- 不许用「关掉权限规则 / 关掉 RLS / CORS 全开」来解决报错
- 预算上限没设好，不算检查完成
