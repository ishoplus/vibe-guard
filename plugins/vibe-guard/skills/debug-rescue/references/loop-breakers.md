# 打破「修 A 坏 B」死循环

## 为什么会循环
| 症状 | 真正的原因 | 解法 |
|---|---|---|
| 修 A 坏 B，修 B 坏 A | A 和 B 共用了同一段代码 / 同一份数据，而两边的需求互相冲突 | 找出共用的那部分，问用户两边到底要什么，然后拆开或统一规则 |
| 每次修完换一个新报错 | 上一次的补丁没撤回，补丁叠补丁 | 回到最后能用的存档，从干净状态重来 |
| 本地可以，线上不行 | 环境不同：环境变量、数据库、版本、网址 | 列出两边的差异逐项比对，先查环境变量 |
| 刷新后好了又坏了 | 缓存、旧的构建产物、多个服务同时在跑 | 清缓存、重启服务、确认只有一个在跑（端口） |
| 时好时坏 | 时序问题（异步还没回来就用了数据）、并发 | 加日志打印时间顺序 |
| AI 改的地方和问题无关 | 上下文里的信息已经过时或太多 | 开一个新对话，只带：复现步骤、报错全文、相关文件 |

## 急救包（按顺序试）
1. **退回最后能用的存档**，把「从好到坏」的 diff 一段一段加回来，看哪一段让它坏掉
2. **开新对话**：把目前已确认的事实写成 5 行交接，丢掉被错误猜测污染的上下文
3. **最小重现**：新建一个最小的文件，只放出问题的那一小段，看问题还在不在
4. **查版本**：`package.json` / `requirements.txt` 里的依赖是否最近被升级过
5. **找人**：把「复现步骤 + 报错全文 + 已排除的原因」整理成一段话，发给懂的人或社区。整理这段话本身常常就能让问题变清楚
