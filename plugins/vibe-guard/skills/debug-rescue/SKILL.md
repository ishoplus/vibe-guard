# 调试救援

新手调试陷入死循环的原因：AI 每次只看局部、猜一个原因、改一下；用户无法判断方向，只能说「还是不行」。
这个流程的核心是**先止血，再用证据定位，不许猜**。

## 执行流程

### 0. 止血：先回到能用的状态
先问用户「大概什么时候还是好的」，再按平台找回那个状态：
- **Claude Code**：如果坏掉的是本次对话里刚改的，请用户按两次 Esc（或输入 /rewind）回到改坏之前那一步 —— 这要用户自己操作，你说明怎么选。rewind 不会还原 Bash 命令造成的改动（删文件、装依赖、脚本生成的文件），这些要靠 git
- **Codex**：没有内置回退，用 git。`git log --oneline -15` 里的 `autosave:` 提交就是每次停下时的存档点
- **两边通用**：`git log --oneline -15` 找「完成：…」开头的存档，那是 small-steps 标记过「能用」的版本
- 如果最近几次修改是在乱试，先向用户提议：「先退回到 {时间} 那个能用的版本，再重新来」。用四段说明讲：要退回到哪里、为什么退回比继续修快、退回之后会丢掉哪些改动、不退回继续修的风险
- 不退回也可以，但要用 `git diff <好的存档>` 看清楚「从好到坏之间改了什么」—— 这往往直接就是答案

### 1. 复现
用白话写下：**做了什么动作 → 期望看到什么 → 实际看到什么**。要求用户提供（或你自己取得）：
- 完整报错文字（不是截图的一部分）
- 浏览器问题：打开开发者工具的 Console 的内容（教用户按 F12 / Cmd+Option+I）
- 能不能稳定重现，还是偶尔发生

复现不了就不要改代码。

### 2. 收集证据
- 在可疑路径上**加日志**（打印关键变量、确认代码有没有走到这里），跑一次，看输出
- 读报错的**第一条**和**指向项目自己代码的那一行**，不是最后一行
- 查依赖版本、环境变量有没有读到

### 3. 缩小范围
用二分法：问题出在前端还是后端？是这个函数还是它调用的函数？是新数据才有还是全部都有？
每一次缩小都跟用户同步一句：「现在确定问题在 {哪里}，不在 {哪里}」。

### 4. 假设 → 验证
写下**一个**具体假设（「因为 X，所以 Y」），设计一个能证明它错的检验，跑。
证实了才改代码；否定了就回第 2 步。**同时只验证一个假设。**

### 5. 修复与收尾
- 修复后按原复现步骤再跑一次，并检查 git diff 里之前的好功能没被波及
- 移除调试用的日志
- 用白话告诉用户：**真正的原因是什么 / 为什么之前的修法没用 / 以后怎么避免**

## 资深模式
session 显示「资深模式」时：校验、检查、确认步骤一律照做，只省略教学性说明（白话类比、四段说明、术语解释）。本技能具体差异：
- 流程与纪律不变：先复现、凭证据改、一次一个假设、两次失败熔断
- 不解释 rewind / git 的用法，直接说用哪个存档点、会丢哪些改动
- 同步进度时用技术语言，例如「已排除：前端、缓存；当前假设：连接池耗尽」

## 硬性纪律
- 没有复现、没有证据，不许改业务代码
- 一次只改一个地方、只验证一个假设
- 修复失败时，把失败的改动**撤回**再试下一个，不要层层叠加补丁
- 连续 3 个假设都被否定 → 停下来，向用户报告已排除了什么、目前的最佳猜测、建议的下一步（包括「找人看一眼」）
