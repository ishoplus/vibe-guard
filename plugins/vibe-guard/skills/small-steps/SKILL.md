# 小步开发

新手项目最常见的失败方式：AI 一次改一大片，「看起来能用」就收工，问题要等很久以后才一起爆出来。这个流程把每个功能压成「可验证的小步」，并且逼 AI 如实说出还有哪里没验证。

## 执行流程

### 1. 说方案（动手前）
用 3–5 句白话说明：
- 要做成什么样（用户会看到什么变化）
- 会动哪些地方（「会改首页和存数据的部分」，而不是一串文件路径）
- 有没有取舍需要用户拍板（例：「要不要让别人也看得到？」）
- 方案里包含用户可能觉得多余的步骤（加测试、加权限规则、分开测试数据库等）时，这一步用四段说明讲清楚「为什么要多做这一步、不做会怎样」，标准讲法见 `../explain-plain/references/why-library.md`

琐碎改动（改文字、改颜色）可以跳过这步直接做。其余情况等用户点头。

### 2. 拆步
超过一件事就拆，每步都要满足「做完能单独验证」。告诉用户一共几步、现在在第几步。

### 3. 每步：做 → 跑 → 看
- 先找项目里**是否已经有类似的写法**，有就沿用，不另起一套
- 做完**实际执行**：跑起来、打开页面、调用一次、跑测试。能用浏览器工具亲自点就亲自点
- 验证失败 → 修；同一个问题连续两次没修好 → 停，改走 debug-rescue

### 4. 边界检查
功能做完，读 `references/edge-cases.md`，挑出**和这个功能相关**的项逐条过。能实测的实测，测不了的列进报告。

### 5. 存档
功能验证通过后，做一次有意义的存档：`git add -A && git commit -m "完成：{功能，用户视角}"`。
这些存档是之后调试时「回到上一个能用的版本」的依据。
- Claude Code：自动存档默认关闭，这一步是主要的 git 存档来源，不能省
- Codex：自动存档已经在每次停下时 commit 过，这一步仍然要做 —— 它把零碎的存档点标记成「这里是能用的」

### 6. 收尾报告（固定格式）

```
✅ 做好了：{一句话，用户视角}
🔍 我实际验证过：{具体做了什么动作、看到什么结果}
⚠️ 还没验证 / 已知限制：{诚实列出，没有就写「无」}
👉 请你试一下：{给用户一个 30 秒内能做完的手动测试}
➡️ 下一步建议：{一句}
```

## 资深模式
session 显示「资深模式」时：校验、检查、确认步骤一律照做，只省略教学性说明（白话类比、四段说明、术语解释）。本技能具体差异：
- 第 1 步只在较大改动时给一句话方案（跨模块、改数据结构、改公共接口、改表结构）；小改动直接做
- 第 3、4、5 步（实测、边界检查、存档）照做 —— 这是校验，不省略
- 收尾报告精简为：改了什么 / 已验证 / 未验证 / 已知限制；不写「请你试一下」「下一步建议」，除非有必须做的事

## 硬性纪律
- 没有实际运行过，不许说「完成」「已修复」「可以了」
- 禁止用 try/catch 吞掉错误、写死假数据、改测试迁就代码 —— 细则见 `references/honesty-rules.md`
- 一次改动如果要动超过 5 个文件，先停下来跟用户确认这是不是必要的
