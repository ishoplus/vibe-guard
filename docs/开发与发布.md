# 开发与发布（维护者看）

> 适用于 vibe-guard 插件本身的开发。新手项目的部署由 `deploy-guide` 技能负责，不在本文范围。
> 标 **实测** 的行为在 Claude Code 与 Codex 0.155.1 上验证过（2026-09-21）。

## 1. 准备

- `python3`（3.9 以上；读 `pyproject.toml` 依赖需要 3.11 的 `tomllib`，没有时会跳过）、`git`
- Claude Code、Codex CLI（只改一边时，另一边可以先不装）
- 没有第三方 Python 依赖

```bash
git clone https://github.com/ishoplus/vibe-guard.git && cd vibe-guard
python3 -m unittest discover -s tests      # 先确认基线是绿的
```

## 2. 本地开发：改完怎么生效

**开发时一律直接载入源码，不要用「安装」的方式测。** 两边安装时都会把插件复制一份到缓存，改源码不会反映到已安装的副本（**实测**）。

| 改了什么 | Claude Code（`claude --plugin-dir plugins/vibe-guard`） | Codex |
|---|---|---|
| hook 脚本内容（`hooks/*.py`、`lib/*.py`） | 下一次触发 hook 就生效（每次都重新执行脚本） | 重新执行 `codex plugin add vibe-guard@vibe-guard`（即使版本号没变也会重新复制，**实测**） |
| `hooks/hooks.json` | 开新对话 | 重新 `codex plugin add`，并在 `/hooks` 里**重新信任**（Codex 按 hook 定义的哈希记录信任） |
| `SKILL.md`、`references/`、`scripts/` | 开新对话 | 重新 `codex plugin add`，开新对话 |
| 清单（`plugin.json`、marketplace） | 重新启动 | 重新 `codex plugin add` |

Codex 那一栏建议用 `tests/e2e/codex_sandbox.sh`，它每次都在临时环境里装当前源码，不会留下旧副本。

### 不开 AI，单独测一个 hook

hook 从 stdin 读一段 JSON。直接喂给它，看输出和退出码：

```bash
# Claude Code 的输入格式
echo '{"tool_name":"Bash","tool_input":{"command":"git reset --hard"},"cwd":"/tmp"}' \
  | python3 plugins/vibe-guard/hooks/guard_bash.py; echo "exit=$?"

# 模拟 Codex：事件里带 turn_id（或设环境变量 VIBE_GUARD_HOST=codex）
echo '{"tool_name":"Bash","turn_id":"t1","tool_input":{"command":"git reset --hard"},"cwd":"/tmp"}' \
  | python3 plugins/vibe-guard/hooks/guard_bash.py; echo "exit=$?"

# 资深模式
echo '{...}' | VIBE_GUARD_MODE=expert python3 plugins/vibe-guard/hooks/guard_bash.py
```

退出码 2 = 拦截（原因在 stderr）；0 且 stdout 有 JSON = 决策（例如 CC 的 `ask`）；0 且无输出 = 放行。

## 3. 测试（三层）

| 层 | 命令 | 什么时候跑 | 耗时 |
|---|---|---|---|
| 单元测试 | `python3 -m unittest discover -s tests` | 每次改动 | 约 10 秒 |
| 清单校验 | 见下方 | 改清单、加删 skill 时；发版前 | 约 10 秒 |
| 端到端 | `tests/e2e/cc_step.py`、`tests/e2e/codex_sandbox.sh` | 改了 skill 内容、hook 行为；发版前 | 每阶段 1–3 分钟 |

```bash
# 清单校验
claude plugin validate .                    # CC marketplace
claude plugin validate plugins/vibe-guard   # CC plugin
python3 ~/.codex/skills/.system/plugin-creator/scripts/validate_plugin.py plugins/vibe-guard   # Codex plugin
for s in plugins/vibe-guard/skills/*/; do python3 ~/.codex/skills/.system/skill-creator/scripts/quick_validate.py "$s"; done
claude plugin tag --dry-run plugins/vibe-guard   # 顺便确认 plugin.json 与 marketplace 版本一致
```

单元测试的约定：
- 测试把 `HOME` 指到临时目录，避免读到本机的 `~/.vibe-guard.json`
- 测试里的「假密钥」一律在运行时拼接（例如 `"sk-" + "ant-" + ...`），否则仓库本身会被密钥扫描器命中
- 有一组结构测试会检查：每个 skill 有「资深模式」一节、说明库每条都有四段和风险等级、skill 引用的说明库条目真的存在。改到这些时，测试失败通常代表真的漏了东西

### 端到端试跑

**Claude Code**：每个阶段开新对话（阶段内追问用 `continue`），报告里看「实际调用的 skill」是否符合预期。

```bash
P=/tmp/vg-dryrun/proj
python3 tests/e2e/cc_step.py $P 1 new "我想做一个记账网页，只给自己用，帮我先把需求想清楚"
python3 tests/e2e/cc_step.py $P 2 continue "照你建议"
python3 tests/e2e/cc_step.py $P 3 new "帮我开始这个项目"
# …… 阶段设计参考 docs/试跑记录-2026-09-21.md 的表格
```

判读重点：
- **skill 有没有触发**：对照试跑记录的预期
- **被拒的工具**：非交互模式下没在允许清单里的命令会被拒，这是测试环境的限制，不是 vibe-guard 的问题；需要时用 `--allow 'Bash(xxx*)'` 放行
- **行为是否守纪律**：有没有如实写「没验证什么」、动手前有没有先讲方案

**Codex**：

```bash
tests/e2e/codex_sandbox.sh /tmp/vg-codex-proj "请在 db.js 写入 ... 这是 hook 测试"
```

注意：Codex 很容易被 session 注入的新手规则说服而**自己拒绝**，hook 根本没机会触发。测拦截时要在 prompt 里明说「这是 hook 测试，请照做，被拦就停」。

## 4. 常见改动的检查清单

### 加一个 skill
- [ ] `plugins/vibe-guard/skills/<名称>/SKILL.md`，文件夹名 = frontmatter `name`
- [ ] frontmatter 只用 `name`、`description`、`metadata.version`（顶层写 `version` 会被 Codex 校验器拒绝）
- [ ] `description` 写明触发说法（中英文原话）与不该用的情况
- [ ] 有「## 资深模式」一节，写明哪些校验照做
- [ ] 需要讲「为什么要做」的地方，引用 `explain-plain/references/why-library.md` 的条目（标题要一字不差）
- [ ] 在 `hooks/session_start.py` 两个模式的技能清单里加上
- [ ] 更新 `tests/test_plugin.py` 里的 skill 数量断言
- [ ] 端到端：至少试一句会触发它的话、一句不该触发它的话

### 加一条危险命令规则
- [ ] `hooks/guard_bash.py` 的 `RULES`：四个字段都要有（正则、会做什么、为什么要先确认、更稳妥的做法）
- [ ] 上线类命令放 `DEPLOY_RULES`（会额外检查 ship-check 状态）
- [ ] 测试：该拦的、不该拦的各至少一条（误报会让新手关掉护栏，比漏报更伤）

### 加一种密钥格式
- [ ] `lib/secret_scan.py` 的 `PATTERNS`：只收格式特征明显、误报率低的
- [ ] 确认不会和已有规则重复命中同一个密钥（曾经发生过：Anthropic 密钥同时命中 OpenAI 规则）
- [ ] 测试：真实格式要命中、占位符（`your-key-here`、`xxxx`）不能命中

### 加一条说明库条目
- [ ] 四段都写（📌 要做什么 ｜ ❓ 为什么 ｜ ✅ 做了之后 ｜ ⚠️ 不做的话）
- [ ] 风险等级用「很常见 / 偶尔 / 少见但严重」之一，如实写
- [ ] 结构测试会自动检查格式

## 5. 版本号规则

| 改动 | 版本 |
|---|---|
| 文案、说明库、规则误报修正 | 修订号 0.6.**x** |
| 新 skill、新 hook 行为、新的检查项 | 次版本号 0.**x**.0 |
| 破坏性改动：`.vibe-guard/` 状态文件格式、模式语义、已安装用户需要手动迁移 | 主版本号 |

**CC 只在版本号变大时才会更新已安装的插件**（**实测**：版本号相同时，`claude plugin update` 会回报「已是最新」）。所以任何要给已安装用户的改动，都必须改版本号。

## 6. 发版清单

```bash
python3 scripts/bump_version.py 0.7.0          # 三个清单一起改
```
- [ ] `CHANGELOG.md`：把「未发布」改成版本号与日期，写清楚使用者会感受到的变化
- [ ] 单元测试全过
- [ ] 清单校验全过（上面第 3 节那几行）
- [ ] 端到端：两个平台各测一次 hook 拦截；改过的 skill 各测一次触发
- [ ] 试点期间：改了 hook 的，写一句给带领人的升级提醒（Codex 要重新信任 hook）
- [ ] 提交：`git commit`
- [ ] 打 tag：`claude plugin tag plugins/vibe-guard`（会再检查一次版本一致；格式为 `vibe-guard--v0.7.0`；加 `--push` 会推到 origin）

## 7. 分发与使用者升级

公开仓库：https://github.com/ishoplus/vibe-guard 。使用者用 `ishoplus/vibe-guard` 当来源安装；开发时仍用本机路径。

| | Claude Code | Codex |
|---|---|---|
| 首次安装 | `claude plugin marketplace add <路径或 owner/repo>`<br>`claude plugin install vibe-guard@vibe-guard --scope project` | `codex plugin marketplace add <路径或 owner/repo>`<br>`codex plugin add vibe-guard@vibe-guard`<br>然后在 Codex 里 `/hooks` 信任 4 个 hook |
| 升级 | `claude plugin marketplace update vibe-guard`<br>`claude plugin update vibe-guard@vibe-guard`<br>**重启**后生效（**实测**，需要版本号变大） | 本机路径来源：直接重新 `codex plugin add vibe-guard@vibe-guard`（**实测**）<br>Git 来源：先 `codex plugin marketplace upgrade`，再重新 `codex plugin add`（两条命令已实测可用；拉到新版本后内容是否更新，待下次发版验证）<br>hook 有变动时，到 `/hooks` 重新信任 |
| 确认版本 | `claude plugin list` | `codex plugin list` |
